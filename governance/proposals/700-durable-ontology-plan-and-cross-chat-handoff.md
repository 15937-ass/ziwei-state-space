## Motivation

把本体设计路线、执行边界和恢复方法保存在 GitHub，使换对话、超时或更换模型后仍能接着工作。PI 通过中文成果与具体例子判断理论含义和研究方向，普通 Git、分支、测试和记录工作由执行者完成。

本文是长期计划和交接契约，不能代替实时任务队列。读取顺序、权威层级和槽位规则继续使用现有仓库机制。计划落库不代表 W1–W8 已完成，也不代表本体、映射或产品已获准运行。

## Goals

- 保存 W0–W8 的目标、责任工作线、交付物和验收边界。
- 用简短的条件入口连接启动文件、本文和实时 Issue；普通对话只加载所需材料。
- 复用已有来源、Core 和 Product 成果，避免换聊天后重复抽取、重复创建任务。
- 区分知识覆盖、可执行推断、内部复现和现实验证四种进度。
- 让 PI 只处理需要领域判断的具体问题；每次收工给出三条线状态和一个优先建议。

## Non-Goals

- 本次不选择 A/B/C，不批准通用应象根、共享语义原语、关系或元数据含义。

- 不整体迁移到 RDF/OWL/SKOS/PROV-O/SHACL；继续使用现有 JSON/YAML/Python/pytest，按被证明的需要借鉴标准。

## Current Problem

有来源依据的文字并不天然属于同一类对象。职业发展过程、行动条件下的结果、职业场景、迁移方向、跨宫前提和具体案例不能被一个方便查询的词自动变成相同事件。原文、规范化解释、概念、规则和运行输出也需要分别追踪。

两个瓶颈必须分开：
1. 本体问题：如何组织、区分和查询来源支持的概念及其关系。
2. 可执行性问题：规则的前提、时间范围、情境和运行事实是否足够明确。

解决第一个问题不会自动解决第二个问题。材料增多、接口存在和测试通过，分别只能证明对应范围的工作；不能推导出现实预测有效。

## Proposed Design

### 1. 总体方向：需要检验的建议

- 优先检验来源本位的概念家族／多根森林，即原 B 方向。
- 在具体查询需要或明确治理不变量支持时，逐步加入正交元数据，即收窄的 C 方向；不预先冻结全部轴。
- 对通用语义根，即原 A 方向，要求能力问题和比较证据支持后再决定。
- 技术上的统一输出接口可以服务不同来源概念；它本身不能证明传统理论中存在共同语义父节点。
- 来源断言、概念、规则和运行输出分别保存；约束不因为被分类就成为独立事件节点。
- 所有归一化和元数据仍接受来源保真审查；多根形式本身也不能保证解释正确。

### 2. 执行归属与复用

本计划不创建新的并行任务。每个后续工作单元仍须经过 Issue -> branch -> PR -> validation -> merge，写入路径遵守所属工作线；一次对话只执行一个有界单元，接受结果后结束，不自动串行开启下一 Issue。

| 阶段 | 责任与复用原则 | 接受边界 |
| --- | --- | --- |
| W0 | 所选工作线恢复自己的实时任务；结束时只读核对三条线 | 恢复完成不等于来源、语义或产品成果被接受 |
| W1–W3 | Knowledge Core；先核对现有 #672 的范围和成果，能复用则在该单元内完善；需要新范围时先完成/重划现有单元，再建立后续 Issue | Core WIP 仍为 1；不重复启动第二个本体工作 |
| W4 | PI 审核具体中文决策包，决定被展示的范围 | 只批准明确列出的内容；默认值、额外关系及运行权限不随之获得批准 |
| W5 | 单独的有界 Core 实施工作 | 只实现 W4 实际批准的契约 |
| W6 | 来源到概念的正式映射由所属 Knowledge 单元负责；Product 接入由独立 Product 单元负责 | 映射先接受到 main，随后 Product 选择、验证和接入；不读取未合并分支作为正式输入 |
| W7 | 所属工作线执行相应验证；现实评估另有方案与证据 | 工程检查、教材复现和现实验证分别报告 |
| W8 | 数据与治理事项按所属路径建立任务 | 真实数据收集前完成相应数据边界，不因顺序编号而拖到最后 |

宫位来源审核可以在 Core 比较和决策等待期间独立进行，继续遵守 PI 已选的逐宫顺序。无需等待十二宫全部审核完才进行有代表性的比较；也不得把没有审核的宫位资料作为已接受证据。Product 可推进已授权的独立工作，但知识更新不会自动刷新活动 KIB。

### W0 — 恢复与基线同步

读取 PROJECT_STATE.yaml、CHATGPT_START_HERE.md、governance/RECOVERY_PRECEDENCE_v1.md、当前执行协议和所选工作线/分片状态。查询实时 Issues/PRs，明确所选工作单元、实现 PR、真实审批边界和现有依赖。

核对 main、分支基线、head 和验证对应版本；保留既有证据，合并或外部变更后重新检查。旧聊天、历史快照、旧绿灯和状态缓存不能覆盖实时记录。同步基线不算完成新知识，也不能盲目重放上次操作。

**交付/验收：** 明确已完成、受阻、待 PI 判断和未核实的内容，给出一个符合槽位与输入边界的下一步。无法核实时标明原因。

### W1 — 能力问题与范围

在 Core 单元中编写 10–15 个具体能力问题和非目标，覆盖来源追踪、原文与归一化、前提条件、过程/场景/事件、冲突、未知、跨宫依赖、候选升级，以及来源可能性和经验概率的区别。

每个新增字段或概念必须回答其中一个问题，或满足一个明确治理不变量；不得因为名词听起来完整而新增抽象。

**交付/验收：** 能力问题、非目标及对现有结构的复用清单；PI 可以理解这些问题将带来什么能力，此时不冻结本体含义。

### W2 — 最小数据契约

先检查现有结构是否已经承担 SourceSpan、SourceAssertion、NormalizedClaim、CandidateConcept、MappingProposal、RuntimeRule、EmpiricalObservation 的逻辑责任。它们是待核查的职责，不是要求新增七套类或文件。

分别表达来源支持、归一化方法、语义类型、处理/审批状态、经验验证状态。UNKNOWN、字段缺失、冲突和不适用分别保留；派生记录追踪来源、处理活动、版本和父证据。

**交付/验收：** 最小契约草案及与现有对象的对应关系。对拟议字段列出含义、允许值、缺失处理和迁移影响；新增共享语义不因“只是字段”绕过审批。

### W3 — 非生产 A/B/C 比较

检查来源覆盖与选样依据后，选择约 30–50 条有代表性的来源记录。包含过程、行动条件结果、职业场景、方向/领域断言、跨宫约束、案例型证据、前提缺失、冲突、未知和容易误分类的例子。

只在非生产样本中比较：
- A：共同语义根。
- B：来源本位根森林。
- 收窄的 C：根森林加有需要依据的元数据。

公平比较技术统一入口和语义统一根，不能把两者混用，也不能预设某方案必胜。可以使用试验局部标识，禁止分配正式本体节点 ID、更新 Product 注册表/锁或启用运行消费。

**硬性检查：** 场景不升级为个人事件；前提不丢失；案例不提升为普遍规则；不编造概率；未知不变成否定；未批准候选不进入运行。

**交付/验收：** 能力覆盖、查询复杂度、映射歧义、维护/扩展成本和失败例子。小样本比较是工程设计检验，不能证明现实预测有效。

### W4 — PI 决策门

在中文包中展示：
- 具体选项、原文依据、归一化解释和实际例子；
- 试验结果、失败情况以及各方案会允许/禁止哪些推断；
- 本次选择范围、非目标、关系语义及元数据允许值和缺失处理；
- 迁移、版本、兼容与回滚安排；
- 哪些获得授权，哪些仍然未获授权。

PI 判断的是研究含义和后果，不负责选择技术字段名称。不能只给 A/B/C 字母要求批准；证据不足时可退回修改或缩小范围。必须先取得明确 PI 决定，再冻结正式本体根、共享语义或关系。

**交付/验收：** 可追溯的 PI 中文决定。批准仅对该包列明的内容生效，不自动批准 Product 运行、经验概率或因果建议。

### W5 — 实施已批准的 Core 契约

只实施获准概念、关系、schema、ID、校验、测试及迁移兼容。保持来源断言、概念、规则和运行输出分离；未决语义显式保留，不以默认猜测补全。

**交付/验收：** 对照批准范围验证的版本化 Core 成果，来源完整性和当前主线/最终 head 检查通过。后续需要扩大范围时另行提出，不在实施中夹带。

### W6 — 映射与产品接入

来源提取和来源到概念的映射分别审查。映射保留条件、时间范围、例外、来源等级、冲突、未知和跨宫依赖。正式映射先在 main 接受，Product 再以独立有界 Issue 选择冻结输入、评估影响、运行相应验证并接受集成。

动态规则另需核对原局前提、时间层、现实情境、运行事实和输出含义是否足够完整。不得为了适应软件契约伪造前提，也不把全部候选保持受阻简单解释为继续增加框架。

**交付/验收：** 优先争取一条有明确来源和完整条件的端到端推断示例，从命盘事实到结论、证据、冲突和未知均可解释；材料不足时交付精确缺口，而非虚构可执行成果。一个宫位或有界领域可以先完成原型，不要求十二宫齐备。

### W7 — 分层验证，贯穿各阶段

持续区分：
1. 来源保真：是否忠实保存原文条件、范围和不确定性。
2. 结构/推断一致性：数据、引用、逻辑和实现是否一致。
3. 教材案例内部复现：是否重现来源中的特定推断。
4. 盲测与前瞻经验评估：是否在独立、预先确定的评价条件下得到现实支持。

前三级不代替第四级。不得使用同一批案例发明规则并声称独立命中；盲测与个性化结果分别报告。概率、因果和行动建议需要各自的证据与审批边界。

**交付/验收：** 版本化证据及各层通过/失败/未知的范围，不能用“测试绿了”概括全部成熟度。

### W8 — 长期治理，相关事项在使用前完成

审查第三方教材/扫描件的使用与分发边界；仓库许可证不能自动授予第三方内容的权利。此处是后续审查要求，不是任何具体法律结论。

在真实用户数据收集或产品化纵向研究前，先定义同意、隐私、访问、删除、缺失及退出处理。冻结数据集、模型和知识包版本，保留否定、未知、失访和删失观察；无回复不自动记为“事件未发生”。

经验不符创建 Knowledge Gap Report，不能静默改写经典来源。只有相关来源复核和应有审批可以改变 canonical 层。

**交付/验收：** 与实际采集和使用范围相匹配的数据治理与版本追踪方案；编号 W8 不代表可以晚于真实数据使用。

### 3. 跨对话恢复契约

当 PI 要求恢复本文计划时：
1. 先按标准启动/恢复顺序确认当前权威规则。
2. 读取本文和 #700 的实时状态、关联 PR；#700 关闭可表示计划交付完成，不表示 W1–W8 执行完毕。
3. 读取相关后续实时单元及其接受成果，核对当前 main、输入版本、槽位和审批条件。
4. 复用已完成工作，仅选择一个可执行有界单元；受阻时提出或选择已授权的独立工作，不能跨线修复或绕过门。
5. 结束前把结果、决定、证据和恢复位置写回所属 Issue/PR，并按 AGENT_WORKFLOW.md §13 只读核对宫位、Core、Product 后用中文报告。

同一单元的检查点至少包含：工作线/分片与 Issue/PR；main/base/head；已接受和未接受的产物、ID/页码/范围；验证命令、环境、结果和运行链接；残余问题、真实审批边界、精确下一步。模糊写入先核对再重试；不可重构的审查成果在停止前持久记录。

只有当 PI 要求恢复本计划，或当前任务明确依赖它时，才从启动入口加载全文；普通 Product/Knowledge 任务继续按自己的 Issue 加载所需材料。本文不要求每次都加载全部书籍、计划或所有工作线历史。

### 4. PI 日常操作卡

PI 可以在新对话中使用：

> 继续紫微斗数仓库的总计划。按 CHATGPT_START_HERE.md 恢复最新状态，再读取 Issue #700 和总计划。沿用已有任务，选择当前已授权且可执行的一项，完成到可审核检查点；需要我作理论判断时先给中文依据和例子。结束时汇报宫位、Knowledge Core、Product 状态及一个优先建议。

执行者负责技术取舍、分支、校验和交接；需要 PI 的是来源解释、流派边界、研究优先级、案例含义和重大产品/理论选择。每次新对话可按实时阻塞机动选择工作线，但一次执行只写一个工作线；不重复开启同一 Issue，不突破现有 WIP 和逐宫安排。活跃执行环境负责推进任务，ACTIVE 标签仅表示任务已启动。

收工报告说明整体阶段，并分别回答三条线能独立做什么、等什么、是否需要 PI；再报告本轮实际成果和一个优先建议。最多列一个近期集成候选，明确其剩余验收条件。进度分别看来源覆盖、可执行能力、完整示例和现实评估，不只累计记录数。

## Alternatives Considered

- 只依赖聊天历史或 PI 记忆：无法可靠恢复实时执行状态。
- 只把提示词保存在个人笔记：可能与 GitHub 漂移，不能成为唯一依据。
- 每次对话加载巨型总提示：增加上下文负担并干扰独立任务。
- 在现有权威链中保存一份版本化计划、一个短入口和实时 Issue：本次采用；不增加竞争状态源。

本节的采用决定只涉及计划如何保存；W3 的 A/B/C 本体选项仍未选定。

## Compatibility

沿用三条写入工作线、路径所有权、既有 Knowledge Core/宫位 WIP 上限、PI 的一次一个宫位安排、串行主线接受和当前执行协议。无新增工作流、自动 push 触发、收费 Runner、写权限或必需检查。

只更新计划文档、条件入口和过期的治理交接指针；PROJECT_STATE.yaml、Product/Knowledge 状态与语义文件均不变。最小治理缓存修正的理由是 #701 -> #700 交接已落实，避免未来把已完成的 #700 当作下一执行任务；仍由实时 Issue/PR 决定实际状态。

## Knowledge Impact
